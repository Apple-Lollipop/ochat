# Desktop build checks

The **Desktop builds** workflow builds Windows NSIS, Linux DEB/AppImage and an Apple Silicon (arm64) macOS APP/DMG. Its Mac job calls the existing **macOS DMG** workflow in `.github/workflows/macos.yml`, which also remains available independently. Mac configuration, caches, tests, signing and bundle verification have one shared definition. It runs interface tests, Rust formatting and the complete core test suite before creating installers. A failing test intentionally prevents packaging.

## File snapshot regression

The old integration test `changed_source_is_not_saved_as_a_valid_file` assumed that a transfer reread the sender's original path. File offers now freeze an authenticated encrypted snapshot. Replacing the original after offering must not affect the promised contents.

The replacement test, `offered_snapshot_delivers_original_bytes_after_source_changes`, checks a same-size replacement and verifies the original offered hash, exact received bytes, unchanged replacement source and removal of the partial download. Snapshot ciphertext authentication and corrupted resume-prefix tests remain enabled. No production transfer code or security check was removed.

Previously, the dedicated **macOS DMG** workflow did not run core tests, so it could pass while all three combined jobs failed on that obsolete assertion. Both workflows now run the complete core suite.

## Linux bundle collection

Tauri writes Linux installers to `target/release/bundle/deb` and `target/release/bundle/appimage`. The former collector only inspected `releases/Linux`, a directory populated by the local Linux helper but not by a direct CI build. This caused collection to fail even after Tauri successfully built both installers.

The collector now uses native Tauri bundle directories first, with the already-staged local directory as a fallback. It matches the exact version and avoids combining a fresh native build with stale staged outputs. Seven isolated fixture tests cover clean Linux CI output, local staging, version rejection, Windows NSIS/executable collection and default/explicit arm64 Mac paths. The default Mac collection ignores older universal bundles.

## Run the corrected workflow

In GitHub Actions, choose **Desktop builds → Run workflow → main**. A new run uses the corrected commit. Re-running an old execution repeats its original commit; an old release tag does not automatically acquire changes pushed to main.

Published tags remain attached to their original source commit so existing release binaries and checksums retain their provenance. The application version is **0.0.3**.

## Automatic GitHub releases

Pushing a new version tag such as `v0.0.4` starts the three builds and automatically publishes a GitHub release after all of them succeed. Pushes to main, manual builds and pull requests produce Actions artifacts only. Main builds also populate reusable default-branch caches for subsequent tags.

The tag must match the versions in npm, its lockfile, Tauri and both Rust packages. The workflow checks this before compilation. It downloads the Windows, Linux and Apple Silicon artifacts from that same workflow run, checks their manifests, sizes and SHA-256 hashes, and requires the Mac signature/architecture validation to have succeeded. It publishes the Windows installer and standalone EXE, Linux DEB/AppImage, Mac ARM64 DMG, and one combined `SHA256SUMS.txt`.

Only the publication job gets repository-content write permission. It uses the built-in `GITHUB_TOKEN`; no personal API key is required. Release notes are generated by GitHub. Uploads stay in a draft until GitHub's asset fingerprints and the tag's source commit are verified. A retry can resume a matching partial draft. Conflicting or incomplete existing assets stop publication instead of being overwritten. An identical already-published release is accepted without modification; a different published release is never replaced. Tags with a prerelease suffix create prereleases.

Draft discovery uses the paginated release list and then the release's stable ID: GitHub's by-tag endpoint only returns published releases. The publisher checks the ID and tag again when reading the draft during upload and publication.

If a publication script bug affects an already-built tag, **Resume verified release publication** can use the corrected automation from main without moving that tag or rebuilding its binaries. Supply the original tag and Desktop builds run ID. The recovery workflow checks that all three platform jobs succeeded in this repository at the tag's exact commit, rejects pull-request artifacts and unrelated failed checks, downloads that run's artifacts, and performs the same manifest/hash/signature checks before resuming the draft. Existing published assets are still never overwritten.

For the next version:

1. Run `npm version 0.0.4 --no-git-tag-version` to update npm and its lockfile.
2. Set `[workspace.package].version` in `Cargo.toml` and `version` in `src-tauri/tauri.conf.json` to `0.0.4`.
3. Run `cargo update --workspace` to synchronize the Cargo lockfile, then `node scripts/release/check-version.cjs`. The check also reads the local package versions in `Cargo.lock`; manifest metadata alone is not enough.
4. Commit the version files, create the tag and push:

```sh
git add package.json package-lock.json Cargo.toml Cargo.lock src-tauri/tauri.conf.json
git commit -m "Release 0.0.4"
git tag -a v0.0.4 -m "Ochat 0.0.4"
git push origin main
git push origin v0.0.4
```

These are instructions for a future release. Commit synchronized versions before tagging; existing published tags keep their original source commit. Publication itself is exercised only by a matching new pushed tag; local tests use a simulated GitHub CLI and never create live releases.

## Build time and shared caches

The original 0.0.2 run spent 475/612/526 seconds on core tests (Linux/Windows/macOS), including compilation, and another 530/515/346 seconds on packaging, including release compilation. Platforms already ran concurrently; serial test and release compilation inside each platform accounted for most of the delay.

GitHub allows a new tag to restore caches from the default branch, but not from a different tag. Desktop builds therefore run on main as well as tags. Push source changes to main ahead of the release so that its build can finish warming the caches. A main push and a tag push issued simultaneously cannot use the cache that the main run has not saved yet. Version changes can still invalidate some compiled outputs; dependency caches and compiler caches reduce that cost rather than skipping compilation checks.

All three platforms use sccache with GitHub's cache backend. Rust target/registry caches are saved from main only to avoid accumulating large per-tag copies; tag and PR builds can restore them. Compilation parallelism follows the runner's available CPUs, capped at four jobs and one job per 4 GiB of memory. CI test builds retain line tables for backtraces instead of full variable/type debug information, reducing test compilation, linking and cache size. Debug assertions, the complete test suite, optimized production settings, signing and release verification remain unchanged. Compiler cache statistics are printed on every platform.

The first run after these cache/configuration changes can still be slow. Actual savings depend on cache hits, dependency/toolchain changes, runner load and final linking. Compare a completed main run with a subsequent unchanged manual run on main before quoting a new build-time target. No faster-build timing has been established yet.

Sources: [GitHub cache scope restrictions](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache), [sccache action](https://github.com/mozilla-actions/sccache-action), [Cargo profile debug levels](https://doc.rust-lang.org/cargo/reference/profiles.html#debug).

## Diagnostics

All three platform jobs use Bash with failure propagation through log pipelines. Interface tests have a 4 GiB Node heap limit, Rust build caches are retained, and jobs have a 90-minute limit. The shared macOS workflow uses `macos-26`, adaptive Rust build parallelism, sccache, the arm64 target, deployment target 11.0 and ad-hoc signing. It builds Apple Silicon only.

Windows and Linux jobs upload their available interface, core and build logs as `Ochat-<runner>-logs`. The shared Mac workflow saves its core, interface, WebKit and build logs and produces `Ochat-macOS-arm64`. macOS binaries are locally signature-checked; ad-hoc signing is not notarization.
